# Bloque 4C-1 · Ensayo reversible en STAGING — procedimiento

**Alcance.** Solo STAGING (`yslhwdlzdknhskawqrtv`). NO ejecutar en Production. NO ejecutar ningún SQL del bloque sin autorización explícita. Este procedimiento no aplica el bloque: lo instala dentro de una transacción, lo prueba y lo revierte.

## Qué hace el ensayo
`pending_review_documentos_seguridad_4c1_ensayo_reversible.sql` (archivo GENERADO por `pending_review_documentos_seguridad_4c1_generar_ensayo.sh`; no se edita a mano) cubre **4C-1 y 4C-1b**:
1. Guarda de seguridad: se detiene sin hacer nada si 4C-1 o 4C-1b ya están aplicados, o si falta la etapa A de 4B.
2. `BEGIN;` → instala 4C-1 → instala 4C-1b (ambos sin su `BEGIN/COMMIT`) → pruebas SQL de 4C-1 (visibilidad, altas, vínculos documentales, **asociación manual con la tabla real `cardiolink_paciente_profesionales_v1`**, Storage, firmados, roles) → pruebas de 4C-1b (Secretaría recibe constancias, certificados, órdenes y reposos heredados **de su profesional asociado** por la RPC administrativa, sin la fila completa ni datos restringidos, y los pierde al desactivar la asociación). Las pruebas 24 y 34 de 4C-1 cubren el acceso de Secretaría solo con asociación activa (tabla, Storage, API directa, historial de envíos) y las nuevas versiones por `source_document_id`; las pruebas 25 a 29 y 35 cubren la función SECURITY DEFINER `cardiolink_historial_envios_documento_v1` (Secretaría propio/ajeno, asociación desactivada y reactivada, owner/admin y médico).
3. **Ejecuta los rollback de ambas partes dentro de la misma transacción** (primero 4C-1b, después 4C-1) y verifica el estado anterior (fila 90): 4 políticas originales en pie, ninguna política/función/trigger nuevos, lista de heredados = `constancia_atencion` y la función del historial de envíos igual a como estaba antes del ensayo (`FALLA 90e`; antes de empezar el ensayo guarda su cuerpo normalizado en la tabla temporal `t_rpc_previa`).
4. `ROLLBACK;` y, en la misma sesión, una sola fila final con el veredicto (`ENSAYO OK: las 26 pruebas…`) y las cifras absolutas de lo que podría haber quedado (todas deben ser 0 y las 4 políticas anteriores deben seguir en pie).
No hay `COMMIT`. El archivo de ensayo no persiste nada.

## Cómo leer el resultado
- Termina sin error y la última fila dice `ENSAYO OK: las 26 pruebas terminaron sin error y no quedo nada persistido` → el bloque se instala, las pruebas pasan y se revierte limpio.
- Un mensaje `FALLA …` (o cualquier error) → la transacción queda abortada: ejecutar `ROLLBACK;`. No se persistió nada. Informar el mensaje exacto.
- `REVISAR: el ensayo no cerró limpio` → ejecutar las consultas de `…_checks.sql` y avisar antes de continuar.

## Cómo se ve el resultado en el SQL Editor de Supabase (hallazgos del 2026-11-12)
- **Una sola consulta multi-sentencia = una sola transacción.** El SQL Editor envía el archivo como UNA consulta: todo (incluida la tabla temporal `t_rpc_previa`, que el archivo crea antes de `BEGIN`) forma parte de la misma transacción y desaparece con el `ROLLBACK`. Verificado en STAGING con una tabla temporal de prueba. Consecuencia: la fila final de veredicto (que lee `t_rpc_previa`) termina con `42P01: relation "t_rpc_previa" does not exist`. **Si el ensayo llega a ese error, TODO lo anterior pasó** (26 pruebas, rollback de 4C-1b y 4C-1, `FALLA 90…`/`90e`): cualquier falla previa lanza antes un `FALLA …` distinto y corta la ejecución. La integridad final se confirma con consultas de solo lectura aparte (políticas, funciones, trigger, lista de heredados, hash de la función del historial, restos `qa4c_*`). Con `psql` (autocommit) la última fila sí devuelve el veredicto.
- El SQL Editor sólo muestra el resultado de la ÚLTIMA sentencia: el listado `SELECT nombre, resultado FROM t_res` no se ve. Cada prueba lanza una excepción si falla, por lo que «llegar al final» equivale a «las 26 pruebas pasaron».
- **Plataforma Supabase:** el trigger `storage.protect_delete` impide todo `DELETE` directo sobre `storage.objects` (42501, salvo que la Storage API fije `storage.allow_delete_query`). Ver la prueba 21 (paso 3.6c) y el QA funcional siguiente.
- Los avisos «Potential issues detected» del editor (operaciones destructivas / tablas sin RLS) se refieren a los `DROP` del rollback y a las tablas temporales del ensayo: elegir «Run without RLS» (no agrega sentencias; «Run and enable RLS» sí agregaría).
- **Precondición de datos de STAGING:** debe existir una asociación secretaria–médico ACTIVA (médico activo con `professional_id`) y un owner/admin activo. La auditoría de la tabla exige un `actor` real (`auth.uid()`): la asociación se activa desde la app con sesión de owner, no desde el SQL Editor.

## Qué demuestra cada capa respecto de «Secretaría no puede borrar» (prueba 21, paso 3.6c)
- **Prueba SQL (ensayo):** el `DELETE` directo sobre `storage.objects` lo bloquea la plataforma con 42501 y mensaje `Direct deletion from storage tables is not allowed…` (se verifica SQLSTATE + mensaje + contexto `storage.protect_delete()` + trigger habilitado; cualquier otra excepción se relanza). **Ese bloqueo no demuestra que la RLS impida a Secretaría borrar mediante la Storage API.** Por eso el ensayo, además, revisa el predicado EFECTIVO: la única política permisiva `DELETE`/`ALL` de `storage.objects` para `authenticated` es `cardiolink_patient_documents_storage_delete`, cuyo predicado usa `cardiolink_can_delete_clinical_document` (solo owner/admin, o médico titular); Secretaría no lo cumple ni con fila ni sin fila ni siendo la autora del objeto, y los controles positivos (médico titular, owner/admin) sí. La prueba 21 queda aprobada como PARCIAL: **requiere verificación posterior por Storage API**.
- **QA funcional posterior (obligatorio antes de dar por cerrado 4C-1):** prueba REAL por Storage API.

## QA funcional posterior: borrado por Storage API (después del ensayo y de aplicar 4C-1)
Nunca un documento real: solo objetos DESCARTABLES de prueba, en la ruta `documents/qa4c_storage/…` del bucket `patient-documents`, creados para este QA y eliminados al final por la Storage API (no por SQL).
1. Con la **sesión de Secretaría** (asociada a un médico), subir por la Storage API el objeto descartable `S1` (`documents/qa4c_storage/S1_<fecha>.txt`; la Secretaría queda como autora). Con la **sesión del médico titular**, subir `S2` (`documents/qa4c_storage/S2_<fecha>.txt`).
2. **Intento negativo:** con la sesión de Secretaría, `supabase.storage.from('patient-documents').remove([S1, S2])`. Resultado esperado: no elimina ninguno (la API devuelve lista vacía o un error de permiso; ambos casos son válidos).
3. **Verificar que el objeto continúa existiendo después del intento** (lectura SQL de solo lectura: `select name, owner from storage.objects where bucket_id='patient-documents' and name like 'documents/qa4c_storage/%'` ⇒ S1 y S2 presentes; y descarga/listado de ambos con la sesión que corresponda). Si alguno falta: FALLA crítica (la RLS de DELETE habilitaría a Secretaría): detener y no aplicar 4C-1 en Production.
4. **Control positivo autorizado:** con la sesión del **médico titular**, `remove([S2])` ⇒ S2 desaparece (demuestra que el método detecta borrados y que el borrado autorizado funciona). Con **owner/admin**, `remove([S1])` ⇒ S1 desaparece. Verificar con la misma consulta que ya no quedan objetos `qa4c_storage`.
5. Anotar resultado, fecha, usuario de cada sesión y el contenido de la consulta de verificación antes y después de cada paso.
